# Setup cleanup after durable publication (#16)

The production `DefaultLibrarySetupService` publication path now attempts staging cleanup only after `LibraryActivation.activateExportedForNextStartup` returns a durably registered managed path. The source archive identity is measured independently from the actual closed archive, and `CompletedLibraryJobCleanup` still independently verifies both full staging files, the persisted preparation and selection proofs, and the managed runtime before deleting its two permitted files. Original catalogue job context is used; reusable acquisition caches, staged/managed runtimes, logs and support receipts remain.

The adapter's internal `Publication` contains the registered path and storage summary. The service immediately returns that registered result after publication, without a cancellation boundary that could misreport the committed selection as cancelled. Cleanup refusal, cancellation, partial removal or an I/O failure produces a visible storage warning while preserving the registered path and success state. Only ordinary exceptions are handled; VM errors propagate. Conservative protection refusals, including extra protected-root mismatches, remain refusals rather than weakening boundaries.

A unique `cleanup-outcome-<uuid>.properties` support receipt is written in the original protected catalogue job. It records registration path/runtime hash, time, complete/partial/cancelled/failed status, known removed bytes/files and warnings. Writes use the same `SetupStorage` job verification, a bounded payload, `CREATE_NEW`, and a forced file channel. A failure to persist this report remains nonfatal and adds a visible warning. Cleanup outcomes do not replace the original preparation evidence.

The completion summary now reports actual removed storage or a cleanup warning, followed by retained runtime/download/log/receipt storage. It no longer claims that the full raw source is always kept. A partial cleanup does not claim that all staging was retained or that the operation can safely retry automatically.

Fifteen direct Java/JUnit adapter tests passed, including six new tests for complete/partial summaries, refused cleanup, failed outcome persistence, cancellation already requested immediately after registration, protected support-report persistence, and propagation of VM errors. These are authored backend bridge tests. They do not claim a fresh production-network service run or final packaged GUI acceptance. The separate genuine helper filesystem acceptance remains documented in `completed-library-staging-cleanup.md`; focused Maven and a fresh service-level production run remain integration checks.
