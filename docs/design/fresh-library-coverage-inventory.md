# Fresh first-library coverage inventory (#14)

The genuine production run documented in `docs/verification/2026-10-18-fresh-java-library-preparation.md` produces a 45,441,024-byte core/client runtime library. It is not a smaller copy of every feature in the older approximately 1.05GB runtime. Its own full-source candidate is 642,269,184 bytes; the compact export preserves that candidate's gameplay tables while omitting raw ingestion payloads.

The measured run selected Questie/native/Wago/Raidbots, leaving AtlasLoot and AllTheThings unchecked. It contains 21,543 items, 13,392 NPCs, 5,232 quests, 596 zone records, 19 native instances and 3,875 catalogue items using proven hotfix details. The native detail coverage gate passes at 91%; source gaps and beta qualifications remain. Selected-source raw evidence and identities are retained in the full candidate and accounted for in compact provenance metadata.

## Existing Java entry points and integration gaps

1. **Native foundation is the first bounded integration.** `FoundationArchiveWorkflow.ingest(database, directory)` validates exact CSV hashes from an acquisition manifest; `project(database, snapshot)` runs `ClientDataset`, item knowledge and `NativeItemMetadataProjection`. The 51 selected CSVs already provide legitimate inputs for a qualified subset, but need a Java adapter into that explicit manifest/path contract. Missing tables stay unavailable. Native-only cards must keep unknown names/details qualified, and final validation must still enforce conservative hotfix exclusions. Additional source tables require reviewed pins and explicit acquisition, not unreviewed extra cache contents.
2. **World hierarchy needs a current-build API.** `WorldMapArchiveWorkflow.ingest/project` is Java and replayable, but its existing context is hard-coded to build `1.60.1.70374` and an ATT source attribution. Do not label newly acquired native `70450` data as that older context. Add a reviewed native-CSV contract for the selected product/build/source and derive hierarchy/bounds from the selected UiMap/UiMapAssignment inputs.
3. **Flight and entrance overlays need a source split.** `MapLayersArchiveWorkflow.ingest/project` consumes five client tables (`UiMapAssignment`, `TaxiNodes`, `TaxiPath`, `TaxiPathNode`, `AreaTrigger`) and a pinned VMaNGOS database/lock. Four tables are outside the present 51-table preset. The current method is not a complete Java network acquisition path and includes independently sourced Vanilla evidence. Implement a separately qualified native flight-table slice or require explicit additional server-source consent; do not silently include VMaNGOS or another edition.
4. **Map artwork and instance floors need materialization.** `IconLoader`/`ZoneMapLoader` read already converted images; they do not obtain and convert native game textures. `AtlasMapsWorkflow.apply/replay` accepts prepared addon map inputs and records floors/legends, but the prepared images/metadata still need a selected, hash-checked Java acquisition/preparation path. Its legacy replay creates temporary files in the default temporary directory; new integration should use protected job storage. Java native table acquisition alone does not supply images or audio.
5. **Collectors are explicitly local observations.** `CollectorArchiveWorkflow.ingest` and `CollectorProjection.project` already capture/replay qualified observations in Java. Integration needs a separately selected collector input, exact provenance/context validation, and no writes into WoW folders. No observations should be invented when that source is absent.
6. **Existing completion/history code needs reviewed support contracts.** `NativeClientItemCompletionWorkflow.project` expects a `blizzard-hotfix` support snapshot plus a native foundation snapshot; the new conservative overlay is archived inside the selected core client role. Reconcile those contracts explicitly rather than mislabeling new evidence as an old support snapshot. `HotfixArchiveWorkflow` and old history tables must not reintroduce the unresolved generic removal policy or Era fallback. Optional ATT/loot projection and `QuestieRefreshWorkflow` remain tied to selected inputs; initial builds need no fake update-history rows.

The safe stage order is core selected projection, selected additive capture/project steps, final whole-candidate validation, then runtime export and independent verification. Each new additive stage needs bounded acquisition, cancellation/progress boundaries, durable input snapshots and atomic job publication. `ArchiveWorkflow.project` deliberately refuses databases already carrying additive projections, so retries must replay from a fresh catalogue job rather than regenerate core tables over additive facts. Update final candidate/export receipts after the last selected additive step, and verify projected IDs/exclusions/source context before activation.

This is an implementation inventory, not a promise that every older history/comparison table belongs in the default new library. #14 should track user-visible capability parity under the user's actual selected sources, with map/artwork/collector availability shown explicitly.
