# Keyboard, compact-window and accessibility review

Reviewed 2026-10-17 against HEAD `52e144e`. This is a source and existing-capture review, not a new live assistive-technology test. No production code was changed and Maven was not run.

## Recommendation

Retain the existing search/history keyboard behavior. Prioritize named navigation, readable narrow-screen content, and explicit labels/state for the new calculators. The app already has substantially more keyboard support than its icon-heavy presentation suggests; the biggest opportunity is making that support visible and consistent.

## Findings and acceptance criteria

| Priority | Finding and grounded evidence | Proposed improvement | Acceptance criteria |
| --- | --- | --- | --- |
| P1 | **Camping loses useful information at narrow widths.** Final `catalog-final/camping-0-dark-420.png` shows truncated camp names, professions and descriptions. `CampingPage.table()` uses six auto-sized columns, single-line cells and mouse tooltips; `PageContent` deliberately tracks viewport width. Preventing horizontal scrolling alone does not make this information readable. | At compact width, use camp cards: full name, profession/tier/rank badges, wrapped description. Keep an optional detailed table in wide layouts. Move the party planner before the long reference tables, or provide section links. | At 420 logical pixels, a keyboard user can read the full camp name, profession, rank and description without hover. Party planner reachable through a visible link within the initial viewport. No horizontal clipping at default and increased text sizes. |
| P1 | **Calculator input controls lack programmatic labels.** `TalentPage` creates a tree combo, build-string field, table, detail area and feedback area without explicit accessible names or `JLabel.setLabelFor`; `SearchBar` likewise has a visual Search label but no label-for relationship or explicit text-field accessible name. Placeholder copy disappears on typing and the visual Search label is hidden in compact mode. Camping explicitly names its profession/rank/member/coverage controls and is a good local pattern. | Name search, talent tree, build string, talent list, selected-talent details and allocation feedback. Associate persistent visible labels with editable controls. Distinguish Talent and Legacy contexts. | Inspect accessible names with text present and absent, in both window modes. Screen reader identifies every control and its purpose without relying on placeholder text. Tab order follows the visible task sequence. |
| P1 | **Transient planning state can be lost during normal navigation.** `TalentPage` owns allocation maps and states “nothing is saved”; `CampingPage` owns its draft locally and states “lasts for this page only.” A player who follows an item/source link or switches section can lose planning work when the page is reconstructed. Warning text describes the limitation, but does not protect the task. | Preserve session-only drafts in a controller/session model; expose Clear/Reset as explicit actions. Show “Session draft” with Export/Copy where applicable. Do not imply character progress or ownership. | Allocate ranks/add party members, navigate elsewhere, use Back, and recover the same draft and selected row. Reset clears intentionally. Restart persistence is a separate product decision. |
| P2 | **Seven icon-only destinations require recall.** `Rail` is fixed at 48 logical pixels with tooltips; it correctly sets each accessible name. This is a discoverability issue, not a missing-accessible-name defect. | Offer a labelled sidebar in the normal window; retain the compact rail as an explicit collapse option. Reveal labels on keyboard focus as well as hover if the icon-only mode remains. | A first-time player can identify Items, Quests, Zones, Dungeons & Raids and Forever without waiting for hover. Every icon retains accessible name and selected state. |
| P2 | **Rail focus is visually ambiguous on the selected destination.** `RailButtonUI.paint()` defines hover/focus only when `!selected`; a selected button therefore paints the same selected styling with and without keyboard focus. | Add a separate focus outline that remains visible on selected buttons and is distinguishable from hover/selection in both themes. | Tab across rail, including selected item: focus location is unambiguous in screenshots and grayscale inspection. Selection does not disappear when focus moves. |
| P2 | **Talent browsing is a dense reference table rather than a clear allocation task.** The final 420px talent capture displays names, numeric ranks and node IDs beside a separate detail panel and several equally weighted buttons. `TalentPage.NodeTable` makes raw node IDs a primary column; prerequisite text uses numeric node IDs. Native display of headers must be checked before treating absent headers in headless captures as a defect. | Promote talent name and rank/max rank, show named prerequisite links, move node/spell IDs to Source details. Add a visible instruction (“Select a talent, then add or remove a rank”) and disabled-with-reason actions where rules prohibit allocation. Keep a keyboard-accessible list even if a tree view is introduced. | Keyboard-only player selects talent, reads prerequisites and allocates/removes rank without understanding source IDs. Reason for blocked allocation is visible and announced. No action relies on color or pointer hover. |
| P2 | **Evidence controls expose actions but not a semantic expanded state.** `SourceDifferencesPanel` uses `JButton`, swaps action names and reveals child panels. This is keyboard-operable through standard Swing buttons, but no accessible expanded/collapsed state or association with the revealed region is explicit. “Show technical source evidence” labels repeat for multiple assertions. | Use a consistent disclosure component with expanded state and uniquely contextual names, e.g. “Show Blizzard hotfix evidence for Strength.” Keep focus on disclosure when opening/closing; provide a concise selected-value summary before full evidence. | Screen reader can identify which field/source is expanded and whether it is open. Space/Enter works, focus remains predictable, collapsed descendants are absent from traversal. Loading next batch preserves focus and announces count. |
| P2 | **New catalog pages have no common section-navigation pattern.** Source evidence, camping, talents and races each construct their own layout. Existing page keyboard shortcuts and source jumps are documented in `KeyMap`, but the new catalog pages do not provide a shared heading/section shortcut structure. | Use shared page header, breadcrumb/back affordance and section links. Add a “Skip to content” / explicit focus-content command; retain Ctrl+F for global search. | From the shell, keyboard user reaches page content without traversing every navigation control; section jumps reveal target and move focus consistently. Back retains history semantics, hierarchy-up remains separate. |

## Existing behavior to preserve

- `RailTest.browseSectionsWithTooltipsAndIcons` verifies all seven labels/tooltips; these are already present.
- `KeyMap` centrally documents Ctrl+F/Ctrl+L/slash search, Alt+Left/Right history, Ctrl+B results, F10 compact mode, text-size controls and other page shortcuts. Help should remain generated from this map.
- `SearchBarTest` covers recent-search focus handling, stale lookup suppression and the Escape chain. Do not regress the deliberate-focus guard that avoids a recent-search popup after a page swap.
- `MainFrame.setDetail`, `focusTargetIn`, `onResultOpened` and associated `MainFrameTest` cover logical focus transfer when replacing a focused page/collapsing the results list. `AppControllerTest` covers history restoration and search/selection flows.
- Existing isolated-X11 report `.local/v041-acceptance/native-final/report.txt` records actual JFrame/Robot focus, Tab, Enter, pointer mapping and Alt+Left/Right map history. Its scope is map navigation in isolated X11, not full keyboard acceptance of every catalog page or the user's Wayland session.
- `RacesPage` uses real named Swing buttons; Camping names profession/rank/member/coverage inputs. `RaceCampingLayoutTest` checks narrow layout geometry. Keep these baselines while improving task presentation.

## Required live validation before calling a redesign accessible

- [ ] At 420px and normal width, use only keyboard for: search → result → item → source NPC → Back; confirm selection, scroll and focus restoration.
- [ ] Allocate/import/reset Talent and Legacy drafts, with sorting enabled; confirm current row, feedback and prerequisite names remain clear.
- [ ] Add/remove five camping members, including no selection and full-party states; confirm useful feedback and draft retention.
- [ ] Open/close source and technical disclosures, load another comparison batch, then return to preceding page.
- [ ] Walk all rail destinations and page controls using Tab/Shift+Tab; focus must never become invisible or trapped inside nested scroll panes.
- [ ] Verify table header rendering in a settled native window. Headless snapshots alone are insufficient evidence of missing headers.
- [ ] Inspect at increased text size and OS scaling; names, action labels, feedback and essential values must remain available.
- [ ] Test a Java-accessible screen reader/bridge on the target desktop. Accessible names in source do not prove announcement order, dynamic feedback or expanded state works.
- [ ] Capture settled pages after asynchronous loading. Native `04-westfall-zone.png` shows a loading transition and should not be used to assess final zone-page content.
