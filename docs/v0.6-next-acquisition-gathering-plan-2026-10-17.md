# Next v0.6 increment: recipe acquisition and recorded object sources

Date: 2026-10-17. Read-only audit of Java code and installed SQLite build `40ca42c8e8c6442c0e2e633f76bf4f4638ebf23faf4029b568ee1ee038c207b7`. This plan changes no application or database data.

## Priority and reuse

First extend the native Crafting guide with teaching-item acquisition. This connects exact-build creation evidence to useful existing vendor/drop/quest pages without pretending to implement trainers or the full profession browser. Next add item-specific object-source geography as a separate bounded view. Both are useful independent increments; neither completes all v0.6 scope.

Already implemented: native creation variants, reagent slots, skill association/thresholds, context-qualified yields and asynchronous lazy Crafting guide. Existing item pages already show Sold by, Dropped by, Quest reward and Contained in; object pages already show their items and spawn maps. Existing normalized `craft`, `craft_reagent` and `craft_recipe_item` provide older selected projections. Do not simply relabel these rows as evidence of the currently pinned Forever recipe relationship.

## Slice A: native teaching items and acquisition links

**Outcome:** from an output item's Crafting guide, inspect how a recorded teaching item relates to that native crafting spell, then open its reported acquisition evidence.

1. For the selected native creation spell, resolve teaching items using only its exact pinned Forever `ItemEffect`, `ItemXItemEffect` and, where needed, `SpellEffect` records. Preserve table path/line, snapshot, build and locale. Reuse the importer `CraftLoader.teachers` semantics as an audited reference, not the older projection as authority.
2. Recognize direct native ItemEffect TriggerType6 for the target spell. For TriggerType0/6 that invokes an explicit native Learn Spell effect36, follow its EffectTriggerSpell to the target creation spell. Do not treat arbitrary use spells or name similarity as teaching evidence. Deduplicate item identities while retaining supporting paths and any recorded conditions; an unhandled condition is not automatic eligibility.
3. Show Teaching items in the existing Crafting guide. Each item links to its normal Item & acquisition page. The smallest implementation needs no new global browser or copy of the entire acquisition UI. Optionally show bounded counts by category from existing normalized source relationships, explicitly labelled reported relationships.
4. Missing teaching links read No teaching item recorded in this pinned native snapshot. This does not establish that a trainer teaches it, that it is automatically learned, or that it is unavailable.
5. Selected item names/fields use the existing sanitized Forever projection. Unknown native names retain Item #ID. Archived Era values must not supply skill/eligibility/price facts implicitly. Distinguish the exact native teaching relationship from legacy/community-reported stock, quest reward and drop relationships.
6. Trainer, profession proficiency, availability phase, stock, purchase cost and drop probability remain unknown unless separately evidenced. `item_vendor` stores only item/NPC membership; an item's buy price is not a vendor-specific offer price.

### Implementation shape

Extend `NativeRecipeGuideRepository.Recipe` with immutable teaching evidence, or add `teachingItems(spellId)` scoped to its snapshot/context. Prefer lazy selected-variant loading if reverse scans are material. `client_table_row` has primary key(snapshot_id,table_name,row_id); reverse JSON fields are not indexed. Filter native tables in SQL, decode only matches, batch ID lookups, cache by database/snapshot/spell and maintain bounded entries. Avoid per-item full-table decoding or parsing archived JSON on the EDT. No schema migration is needed for the first slice; measure cold and warm query cost before adding an index/projection.

Acceptance: the three real examples above; synthetic learn-effect indirection, duplicate supports, irrelevant use spell, foreign snapshot, missing/malformed condition and unknown acquisition cases; source/build labels remain inspectable. Navigation and Back preserve output, selected variant and scroll. Render desktop/420px dark/light; verify no acquisition SQL on normal item page construction or filter changes. A selected native class ability must not be recast as a profession recipe.

## Slice B: recorded object-source geography

**Outcome:** for an item, browse the objects recorded as containing it and their recorded zone locations. This is a safe first gathering-related view, with language matching available evidence.

1. Start from `item_object_drop` and `game_object`, join `object_spawn` by object ID and selected exact zone. Expose Recorded object sources from the existing Contained in section or a lazy Sources on map tab.
2. List object identity/name, zones, recorded coordinate count and an explicit Open object action. The normal object page already provides detailed spawn map/navigation; reuse it. A later in-tab map can show bounded selected-object pins through existing map infrastructure.
3. Filter by zone and selected object; load snapshot off EDT, cancel stale requests, preserve selection on Back. Bound object rows (for example100+sentinel) and displayed coordinate points (for example250+sentinel), with clear overflow disclosure. Use existing `idx_object_spawn_object`/`idx_object_spawn_zone` and item-first primary key for source lookup; inspect EXPLAIN and timings.
4. Call the view Recorded object sources rather than Mining nodes or Gathering nodes. The installed schema has no normalized native GameObjects/Lock/profession requirement proof. Names such as Copper Vein are display labels, not a basis for assigning Mining proficiency, required skill, respawn or gathering mechanic.
5. Do not draw farming routes, estimate yield/hour, assign drop percentages or imply every recorded coordinate is currently active. Coordinates have selected source provenance; this is neither live tracking nor full-world coverage.

Acceptance: Copper Ore → Elwynn → both distinct source objects; selecting Copper Vein displays its own recorded points rather than the chest's; chest remains visible in all-object sources. Unknown/missing coordinates and capped result sets have explicit states. Source qualification, click-to-inspect versus Open navigation, Back, compact layout and asynchronous cancellation follow existing map conventions.

## Remaining v0.6 scope after these slices

These increments do not close the complete profession browser, recursive crafting graph, general acquisition resolver, trainer finder, vendor economics, source-qualified gathering mechanics or disenchanting. Broad recipe browsing should be built on an indexed exact-native projection once measured demand warrants it, not thousands of `forItem` calls. Trainer/stock/Lock data require real source ingestion and review. Continue those as explicit roadmap remainders rather than making the useful first slice wait for missing server-side facts.
