# v0.5 remaining slices: shared loot and preparation

Date: 2026-10-17. Read-only audit of current Java implementation and the installed SQLite build `40ca42c8e8c6442c0e2e633f76bf4f4638ebf23faf4029b568ee1ee038c207b7`. No data or application source was changed for this plan.

## What already works

- `InstanceRepository.detail` includes main encounters and `boss.is_extra_list` entries. `bossLoot` preserves per-list/per-difficulty membership, reported and observed evidence, and existing source-qualified filters.
- The Journal's Bosses & loot page can already select these extra lists. This is not a missing loot import.
- NPC loot already has a collapsed World drops group. `ItemCategories` classifies generic item classes shared by at least 20 NPCs, with unknown or below-10% rates; notable epics/quest items lead. This is a presentation heuristic, not a stored VMaNGOS reference-pool identity.
- The Journal already has a Quests tab using `LoadedInstance.quests`, populated by `quests.byZone(instance.zoneId)`. Quest pages already have prerequisites, sources, giver/objective locations and chains. Do not rebuild these.
- Maps already expose source-qualified entrances and floor maps. Entrance geography is not proof of a lock, key or attunement requirement.

## Slice A: source-reported shared loot workspace

**User outcome:** on an instance guide, distinguish named encounters from source-reported shared lists without mistaking a list for a boss or losing the item-to-list relationship.

1. Add a Shared loot tab/section using existing `BossSummary.extraList` records and the preloaded `BossLoot` snapshot. Preserve each original source list name. Label the whole section Source-reported shared and extra lists; `is_extra_list` alone does not mean trash, all bosses or world drops.
2. Keep encounter lists focused on actual main entries, with a clear route to the new section. Maintain the existing selected-list behavior and keyboard/Back state.
3. Within a source list, reuse class/slot/resistance controls and shown/excluded/unknown counts. If offering All shared lists, deduplicate visual item rows by item ID but retain every membership and difficulty in expandable details; never merge percentages across lists or difficulties.
4. Show source-qualified presence separately from selected Forever item-field knowledge. AtlasLoot/Continued reports do not establish Forever drop confirmation, drop rates, equal probabilities, exclusive groups or eligible mob sets.
5. For extra lists that are actually objects, event entries or special records, preserve names and linked entity IDs when present. Do not invent NPC IDs, assign an object identity from its name, or reclassify every extra list as trash.
6. Empty state: No shared or extra loot list recorded for this instance. Unknown is not proof that no shared pool exists.

**Implementation boundary:** start as immutable derived presentation data from `InstanceDetail` and existing loaded loot. No schema migration or JSON archive scan is necessary. A pure `SharedLootSnapshot` grouping utility and a Journal component can be tested independently. If the current snapshot accessor cannot enumerate modes safely, add one bounded repository snapshot operation rather than N SQL calls on the EDT. Source comparison loading remains off the EDT and preferably on explicit disclosure.

## Slice B: preparation research, reusing recorded quests

**User outcome:** understand recorded instance-related quests, their prerequisites and access-evidence coverage without pretending to know the player's progress.

1. Upgrade the existing Quests tab into Preparation research, with two explicit sections: Recorded quests for this area and Access requirements evidence. Retain exact area-association wording because `quest.zone_or_sort = instance.zone_id` is not proof a quest occurs wholly inside the instance.
2. Reuse the existing quest list and normal quest links. A selected quest may offer lazy prerequisite-chain preview through existing `QuestRepository.chain`, with faction/AND/OR/missing/cycle semantics unchanged. Do not recursively preload all instance quest graphs or offer checkboxes for character completion.
3. Access requirements evidence initially says No source-qualified instance access requirement recorded in this data update. A quest title containing Attunement, a quest reward named Key, nearby spawn, item class, or an entrance pin does not establish a mandatory access relationship.
4. Optional immediate utility: for a selected quest display its **recorded** required/provided items from `quest_source_item` and link those items. Label them Quest required items / Quest provided items, not Instance keys. Distinguish these from quest rewards and item objectives.
5. A genuine access-rule subsection requires a separate explicit model relating instance, requirement kind, target quest/item, conditions, source and version. Populate only from reviewed authored/source-native rules. Unsupported or unavailable rules remain unknown. That is a later data increment, not fabricated completion of this first slice.

## Data limits and release accounting

There are no normalized reference-pool, loot-group-condition or lock/access-requirement tables in the installed database. `map_instance_access` records map access geography. Archived inputs retain source documents but are not a license to infer conditions from names or rescan all source JSON at page load.

Slice A completes a useful shared-list presentation increment; it does **not** complete exact VMaNGOS reference-pool identities, eligible level ranges, group rolls or rates. Slice B completes a preparation research increment; it does **not** establish unknown keys/attunements. Keep those narrower data requirements as explicit open follow-ups before claiming the original full v0.5 pool/preparation scope complete.

Priority agreed for project scheduling: finish and launch the current verified Journal batch, then implement Slice A and Slice B independently. They touch different new presentation components but both route through `JournalDetails.instance`; serialize that final integration and Maven builds. Exact pool/access data research can run independently, using explicit source attribution and the Forever data boundary.
